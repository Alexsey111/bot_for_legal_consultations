# ⚖️ Legal Consultation Bot

### RAG-powered Telegram Bot for Legal Information

AI Telegram-бот для информационных консультаций по
Гражданскому кодексу Российской Федерации.

Система использует Retrieval-Augmented Generation (RAG):
перед генерацией ответа выполняется поиск релевантных
статей в собственной базе знаний.

Вместо того чтобы полагаться только на знания LLM,
система сначала находит подходящий контекст, а затем
передаёт его языковой модели для формирования ответа.

> ⚠️ Проект предназначен исключительно для информационных
> и образовательных целей и не заменяет консультацию
> профессионального юриста.

---

# 🎯 Problem

При использовании LLM напрямую юридический вопрос
передаётся модели без гарантии, что ответ будет основан
на конкретных положениях используемой нормативной базы.

Например:

```text
Пользователь
     ↓
     LLM
     ↓
Ответ
````

Такой подход может приводить к неточным или
неподтверждённым ответам.

---

# 💡 Solution

В проекте используется RAG-подход:

```text
Пользователь
     ↓
Telegram Bot
     ↓
Поиск в базе знаний
     ↓
Релевантные статьи ГК РФ
     ↓
Формирование контекста
     ↓
LLM
     ↓
Ответ пользователю
```

Таким образом, генерация ответа происходит с учётом
найденного нормативного контекста.

# 🔎 Hybrid Retrieval

Одна из ключевых особенностей проекта —
использование нескольких механизмов поиска.

```text
                       User Query
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
      Article Search      BM25      Vector Search
             │             │             │
             └─────────────┼─────────────┘
                           ▼
                    Candidate Documents
                           ↓
                    Context Selection
                           ↓
                         LLM
                           ↓
                      Final Answer
```

### 1. Direct Article Search

Используется для запросов, содержащих номер статьи.

Например:

```text
статья 196 ГК РФ
```

Такой запрос целесообразно обрабатывать напрямую,
без зависимости от семантического поиска.

### 2. BM25

Полнотекстовый поиск хорошо подходит для точных
терминов и формулировок.

Например:

```text
срок исковой давности
```

### 3. Vector Search

Семантический поиск позволяет находить документы,
которые близки к запросу по смыслу, даже если
формулировки отличаются.

Например:

```text
Через сколько лет можно взыскать долг?
```

может быть сопоставлен с материалами,
содержащими терминологию об исковой давности.

# 🧠 RAG Pipeline

После получения пользовательского вопроса
система выполняет последовательность операций.

```text
Question
   ↓
Query Processing
   ↓
┌─────────────────────────────┐
│ Article Search              │
│ BM25 Search                 │
│ Vector Search               │
└─────────────────────────────┘
   ↓
Retrieved Documents
   ↓
Context Construction
   ↓
LLM Prompt
   ↓
Generated Answer
```

Найденные документы используются как контекст
для генерации ответа.

RAG не гарантирует отсутствие ошибок LLM,
но позволяет дополнить генерацию конкретными
документами из используемой базы знаний.

# 🧠 Prompt Engineering

Prompt Engineering используется на этапе
формирования запроса к LLM.

В prompt передаются:

* пользовательский вопрос;
* найденный контекст;
* инструкции по формированию ответа.

Цель — заставить модель использовать найденные
материалы как основной источник контекста,
а не отвечать только на основе собственных знаний.

Prompt-related логика проекта вынесена в:

```text
prompts.py
```

# 🗄️ Why ChromaDB?

Для MVP была выбрана **ChromaDB**.

Основные причины:

* простой локальный запуск;
* не требует отдельного сервера;
* хранение embeddings и metadata;
* удобная интеграция с Python;
* подходит для небольших локальных RAG-систем.

Для дальнейшего production-развития возможна замена
на специализированные решения, например:

```text
Qdrant
pgvector
Milvus
```

При этом замена vector store не меняет саму
концепцию retrieval pipeline.

---

# 🔤 Why BM25 + Vector Search?

Vector Search хорошо работает с семантическим
сходством.

Но некоторые запросы требуют точного
совпадения терминов или идентификаторов.

Например:

```text
статья 196
```

или:

```text
срок исковой давности
```

Поэтому используется комбинация:

```text
BM25
   +
Vector Search
   +
Direct Article Search
```

Это позволяет сочетать:

* точное совпадение;
* полнотекстовый поиск;
* семантический поиск.

## 7. Answer checks and thresholds

Четыре проверки перед отправкой ответа: ссылка на статью, отсутствие выдуманных
статей, длина и оговорки. Плюс порог «вопрос вообще про ГК?» — он стоит **до**
поиска.

| Переменная | Описание | По умолчанию |
|------------|----------|--------------|
| `CHROMA_PERSIST_DIR` | Путь к локальной базе Chroma | `./chroma_legal_db` |
| `RELEVANCE_HARD_COSINE` | Жёсткий порог близости: ниже — вопрос считается не по теме | `0.33` |
| `RELEVANCE_SOFT_COSINE` | Мягкий порог, ниже которого нужна проверка покрытия слов | `0.45` |
| `RELEVANCE_MIN_COVERAGE` | Доля значимых слов вопроса, найденных в статьях | `0.34` |
| `STRICT_UNCERTAIN_WORDING` | Строгий режим оговорок: отклонять ответ вместо пометки | `false` |

**Не по теме.** Если лучший найденный фрагмент далёк (косинус ниже
`RELEVANCE_HARD_COSINE`) или средний и при этом ни одно значимое слово вопроса
не встретилось в тексте статей — бот отказывается отвечать. Пороги измерены,
а не назначены: на 20 вопросах по ГК лучший косинус был 0.376…0.719, на 12
посторонних — 0.177…0.440 (`tools/qa_threshold_rules.py`).

**Ссылка на статью.** Если в ответе нет ссылки, он всё равно отправляется —
внизу появляется строка «в ответе нет ссылки на конкретную статью, если нужна
точная норма — спросите: „что говорит статья 454“». Отбрасывать такой ответ
хуже: пользователь теряет верный разбор из-за отсутствия формальности.

**Выдуманные статьи.** Ссылки распознаются в любом падеже и в перечислениях
(«статьёй 196», «статей 196, 200»). Если статьи нет в ГК РФ — ответ отклоняется.
Если статья в кодексе есть, но не попала в выборку поиска — ответ отправляется
с пометкой в лог: норма настоящая, просто не была найдена.

**Оговорки.** Слова «возможно», «вероятно», «я не уверен», «обратитесь
к юристу» означают, что однозначной нормы под ситуацию найти не удалось.
Такой ответ **не выбрасывается**: сверху добавляется видимая пометка
«⚠️ В ответе есть слова вроде „возможно“ или „вероятно“: однозначной нормы
под вашу ситуацию найти не удалось». Причина: выбросить верный разбор из-за
одного слова — ухудшение продукта, а не улучшение.

Строгий режим включается переменной `STRICT_UNCERTAIN_WORDING=true` — тогда
такой ответ отклоняется и пользователь получает обычный текст отказа.
Оба режима покрыты тестами (`tests/test_index_and_wording.py`).
